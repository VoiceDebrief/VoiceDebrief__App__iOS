What is built in the sgit app

The reality file for the sgit app. If it is not listed here as built, it does not exist. The design is intention; this page is fact, and it changes in the same commit as the code it describes. The guide in pictures shows the screens with the things to press numbered.

Status words: built is in the repository and proven by a test that ran; unverified is written but has not been proven by a run (of CI, on a device, or against a server, as the row says); proposed does not exist.

Built

Proven by sgit-app.yml, green in all three jobs since run 2 (13 November 2026) and on dev in run 7. Build 0.1.19 (7) was installed from TestFlight on a Mac by the owner on 14 November 2026 and opened: the empty list and the Create sheet were seen. Nothing else has been used on a device, and the app has not yet spoken to a server.

Files over 4 MB in the vault engine builtPackages/SGitVault: VaultStreamCipher.swift (AES-256-GCM as a stream, so a file is sealed and opened from disk to disk), VaultLargeTransport.swift (sgit's upload in parts and download in ranges), VaultLargeFiles.swift (staging, a commit of staged files, download with every check)LargeFileTests on the CI Mac: the stream cipher byte for byte against CryptoKit; tampered files refused; a failed upload carried on; a lost race. sgit-app.yml: sgit clones a vault Swift wrote with files of 5 and 9 MB and verifies its signatures, and Swift reads a vault sgit wrote. All of that is against a folder. The exchange with the live server (signed URLs) is written and unverified: it has been run with sgit itself, not with the Swift code

The list is what was added on the device (kept in the Keychain) and showcase.json from any vault on it. It ships emptyCompiles, and its unit tests pass on the simulators (sgit-app.yml on f7dd58e): the file in both shapes, the links, the grouping, reading it from a vault, keeping an added entry. Playing a video unverifiedUI/FileView.swift, UI/VaultView.swift: a play mark on every video tile; a video's screen opens on a Play button that decrypts it (with progress) and plays it with sound even on silent, with a full-screen button; a frame of the video becomes its tile picture once it has been decrypted, or straight away for videos up to 25 MB. Asked for by the owner on 14 November 2026 after adding videos from his iPhoneNot yet compiled when written. A small picture and the facts beside each file unverifiedEngine/FileFacts.swift, Engine/Outbox.swift: while a file is added, before its plain copy goes, the app makes a small picture (480 pixels: the image itself, a frame of a video, the first page of a PDF or document) and a facts file, seals both like any file and puts them in the same commit. Layout, for any client: .sgit/thumbs/<content hash>.jpg and .sgit/meta/<content hash>.json, keyed by the file's content hash (the 12 hex characters the tree already records), so a renamed or moved file keeps them. Schema sgit.ai/file-meta/v1: name, size, contentHash, contentType, kind, addedAt; for images width, height, orientation, taken, make, model, lens, iso, exposure, aperture, focal length; for video and audio duration, width, height, frame rate, codec, taken, make, model; location only when the person turns on Settings, Keep where photos and videos were taken (off by default); header, every property ImageIO reads from the file's header, flattened, without GPS unless allowed. Folders show the kept picture, reading a few kilobytes, so nobody fetches a large file to see it; the file's screen shows the facts. .sgit/ and names starting with a dot are not listedUnit tests for the picture and facts of a photo, the layout, a QuickTime location, and the outbox writing a facts file per file in the same commit; not yet compiled when written. Files added before this have no picture kept; they are shown as before
Saving a folder out unverifiedUI/VaultView.swift (saveOut, FolderExporter): the three dots on a folder offer "Save these N files to Files" with the size; each file is fetched, laid out as in the vault and handed to the system's export sheet. The share sheet shows the line to paste on a computer (pip install sgit-ai && sgit clone) beside the shown vault keyThe words and the paths have unit tests. Nobody has saved a folder on a device or a simulator
The web Vault inside the app unverifiedUI/WebVaultView.swift: "Open in the web Vault" on a vault's three dots and on a file. The page dev.vault.sgraph.ai/en-gb/vault/?embed=1 is loaded in a web view that keeps nothing, announces itself, and is handed the vault key by a posted message (the web Vault's embed protocol); the key is not in the address. It opens looking only. "Allow changes" hands the page this device's access key for the visit, after a warning; it is not offered for a vault that holds large files, because the web Vault rewrites a folder without the mark that says a file is largeThe protocol was tried on 14 November 2026 against the live page in Chromium with a throwaway vault made by sgit: opened by message, HTML preview shown, a deep link to a file honoured, nothing of the key in the address or in storage, and the access-key event turned "Read-only" into "Synced". The production host vault.sgraph.ai did not answer the handshake. The Swift has unit tests for the words and the host rule; the web view itself has never run on a device or a simulator
A vault's own app, first unverifiedUI/WebVaultView.swift, UI/VaultView.swift: a vault on the server with an app.json (at the top or in .vault/) opens in its own app the first time it is opened in a session, full screen, with an App / Files switch at the top; "This vault has its own app" opens it again. A vault with only an index.html opens on that page in the file browser. Tried on the live page on 15 November 2026: the page loaded decides (/en-gb/app/?embed=1 runs the app, /en-gb/vault/?embed=1 is the file browser) and the message's mode is not used by either; the app page, given a vault with no app, goes to the sign-in page and loses the key, which the app notices and answers by switching to the file browser. Allow changes is offered on the files view onlyUnit tests for where a vault starts and for noticing the sign-in page; tried in Chromium against two published vaults with apps and one without; not yet compiled when written
Show as a gallery, and a gallery page unverifiedUI/PhotoGalleryView.swift, Model/GalleryPage.swift: a vault that is mostly photos and videos offers "Show as a gallery": a full-screen grid of the small pictures kept in .sgit/thumbs, and a viewer that swipes from one to the next, fetching a photo at full size when shown and playing a video when asked. "Add a gallery page to this vault" writes index.html, app.json and gallery.json in one commit, so the vault opens as a gallery in the web Vault and here (the page reads with sg.vfs.read/readText, sets pictures from script, uses no network)Unit tests for the page's contract; the page has not been opened in the web Vault yet; not yet compiled when written
Moving files unverifiedModel/MovePlan.swift, UI/MoveSheet.swift, VaultShelf.move: "Select files to move" on a folder's three dots, choose files and folders, Move to a folder in the vault, the top, or a new one; the whole move is one signed commit ("Move 12 files to photos/day-2"), the same objects under new names, so nothing is uploaded again and the thumbnails and facts kept by content stay with them; a name already taken there is refused unless the person chooses to give the moved ones the next free nameUnit tests for the plan (shape kept, clashes, a folder into itself); not yet compiled when written
Where a file is unverifiedWhereTheFileIs in UI/VaultView.swift, VaultShelf.cacheVersion: a small mark on each file's tile and row in a vault on a server: a green tick when it is on this device (opened, played or saved once and kept decrypted in the cache), a ring while it is being fetched, a cloud with an arrow when it is only on the server and would be fetched when opened; no mark in a vault that lives only on this device. A file this device uploaded shows the cloud: its plain copy is removed once it is encryptedNot yet compiled when written
Your activity unverifiedEngine/UsageLog.swift, Engine/DeveloperLane.swift, Engine/LaneCrypto.swift (all three copied from VoiceDebrief), UI/ActivityView.swift under Settings: every screen opened and for how long, and about thirty actions (create, add, forget, send to the server, pick, retry, discard, open, share, show a key, save out, refresh), kept in a file on the device; a button sends the report, encrypted to the developer's key, over the developer's lane as sgit/usage/v1. Ids and times only: no file name, vault name or keyThe log, the report's shape and the lane message have unit tests. Nothing has been sent from a device, and nothing is sent without the button. Each device keeps and sends its own log; they are told apart by a random install id
Ask this vault, an experiment unverifiedEngine/VaultAsk.swift, UI/AskVaultView.swift, on a vault's three dots: one question to Apple's on-device model (Foundation Models), in a fresh session, which may call four tools that read a copy of the vault's listing and history (a summary, one folder, recent changes, files by name). Every call and what it returned is shown under the answer. The model is given names, sizes and commit messages, never a file's contents; it cannot change anything; nothing leaves the deviceThe tools' unit tests pass (6b13fcb). The model has never been asked anything by this app: CI's simulators have no Apple Intelligence, and nobody has run it on a device. Whether its answers are any good is the experiment
People unverifiedThe people session's screens (Sources/People/, on the shared SGitPeople package): a People row on the home list with the unread count; You (your card as a QR code and a link), Contacts (add by scanning, a picture or pasting; a photo of the person, on this device only), Inbox; Keys and access (an access key, keys given or received, who holds which) reached from SecretsThe screens compile and the app's tests pass (the people session's runs 53 and 60); wired here, not yet compiled when written. Nothing has run on a device; making an inbox and sending use the live server only once a person holds an access key
Who you trust, and shared vaults for people unverifiedSources/Team/: a "Who you trust" row on the home list draws you in the middle and each contact around you with their photo (an agent as a chip), the line between solid and thick when fingerprints were checked face to face and they have written to you, solid when both sides hold each other's card, dashed when only you hold theirs; a person's page says how you met and what is missing. "Make a shared vault with some of them": choose people whose inbox you know, name it; the app makes the vault, puts it on the server, writes .sgit/members.json (schema sgit.ai/members/v1: names, key fingerprints, who added whom, never keys) and sends each person the vault key sealed to their key. A vault with members says "Shared with …" at the topUnit tests for the links, the layout, the summary and the member list; not yet compiled when written. Nothing has been sent to a real person. On the receiving side, "Open this vault" on a received invitation (the people session's) adds it to the list of vaults through the same check as pasting a key
Secrets unverifiedSources/Secrets/: a Secrets row on the home list; every vault with a secrets/ folder, grouped, searchable; kinds login, device passcode, Wi-Fi, card, note, token, vault key, read key, access key, recovery codes; add, change and delete, each one signed commit of one encrypted JSON file (sgit.ai/secret/v1), read into memory, never into the file cache; hidden values behind Face ID or the passcode, copied for two minutes; "Make a strong password"; "My secrets" made on this device with the first secret; the app covered when not in front (the home stack; a sheet open at the time is not yet covered)Unit tests for the format, the paths, the kinds and the password maker; compiles and the tests pass (6b13fcb). Nobody has used it on a device. Sync between devices (issue 122), sharing with people (124) and AutoFill (125) are not built
Questions for you unverifiedUI/QuestionsView.swift, Resources/sg-questions.json: questions from the people building the app, on the home list and in Settings; answer by choosing, typing, or the keyboard's dictation; sent sealed over the developer's lane as sgit/answer/v1Unit tests for the bundled questions and the lane message pass (6b13fcb); nothing has been sent from a device
Guide and what is new unverifiedSources/Guide/ (copied from VoiceDebrief's, the Sherpa session's work), a row on the home list: what changed in each version, the feature guides with numbered pictures (four: getting started, inside a vault, sharing, secrets), and every idea with where it stands, from sg-versions.json, sg-guides.json and sg-ideas.json, which the site's generator writesA unit test that the app's own data loads; not yet compiled when this row was written
The same vaults on every device unverifiedEngine/SecretStore.swift (two homes, after VoiceDebrief's), Engine/VaultShelf.swift: each vault that is on a server is also kept as its own iCloud Keychain item, and the access key too, so an iPhone, iPad and Mac on one Apple account open the same vaults with nothing to set up; a vault only on one device is not carried until it is on the server; new vaults from other devices are picked up when the app comes to the front, and vaults already open are read again then; forgetting a vault takes it out of iCloud Keychain; a switch in Settings. "My secrets" is marked by a file so another device finds it, and goes to the server at once when there is an access keyUnit tests with two simulated devices sharing one iCloud Keychain pass (6b13fcb). Never run across real devices. iCloud Keychain carries items on Apple's schedule, usually within a minute
Sharing a vault unverifiedUI/ShareVaultView.swift: the vault key and the read key as text and QR code, with what each gives; a link for the web Vault UIThe link's form has a unit test. Whether the web Vault UI opens a vault this app wrote has not been tried
History unverifiedUI/HistoryView.swift: commits, signature, the signing key's fingerprint, whether it is this device's, what changedWhat it shows has unit tests; the screen has never been seen
