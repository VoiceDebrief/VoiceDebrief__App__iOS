1. What is being built

A native iPhone and iPad app that does VoiceDebrief's one job (voice note in, transcript and short debrief out) with no OpenRouter, no API key and no inference server: Apple's on-device speech-to-text does the transcript, Apple Intelligence does the debrief. Results are kept in an sgit vault the user owns, opened with a passkey exactly as pki.sgit.ai does it, and the user has one identity: one sgit key bundle (an encryption pair and a signing pair) that signs what the app produces.

In the product's own vocabulary this is the third privacy mode, the one the web app only has as a proposal: device-local. Audio and transcript never leave the device for inference. The only thing that leaves is ciphertext, to the vault server, and only once the user has a vault.

  • Infographics (the web step calls an image model; there is no on-device equivalent to rely on).
  • Speaker diarization. Apple's speech stack does not provide it; MeetScribe does not have it either.
  • Chat over a transcript, personas, web of trust, registering in the pki.sgit.ai register from the app.
  • Sealing a debrief to another person's key (milestone 6, after v1).
  • Android, Mac Catalyst, watchOS.
  • Any payment. With no inference cost there is nothing to bill, which also keeps the app clear of the App Store commission question the strategy brief raised.

3. What already exists, and what does not

Facts the plan rests on, each from a source read for this document.

The web pipeline (exists). website/app/workflows/standard.json is a state machine: normalise, ingest, transcribe, classify, translate (only when needed), summary, infographic (only when asked). All inference is OpenRouter from the browser with the user's own key. Prompts are markdown files in website/app/prompts/. The summary is markdown with exactly three sections: ## Key points (3 to 6 bullets), ## Actions (- [who] what, or - none mentioned), ## In one sentence. Classify returns a validated JSON shape (language with confidence, up to 5 topics, register, sentiment, urgency, signals, a summary line). Results are held in memory only; there is no history.

MeetScribe (exists). Adds the conventions worth inheriting: transcript lines are immutable with edits as a revision layer; flags never delete; cost is null, never 0; exports carry a format and version; and the standing caveat, "Written by a model, not a stenographer."

Vaults, PKI and passkeys in the VoiceDebrief repos: none. No vault, crypto, key or WebAuthn code exists in either VoiceDebrief repo. Native apps are an open, unscheduled issue (011) with no repo name or structure decided. Everything in sections 5 to 7 is built from the sgit estate, not from VoiceDebrief code.

The passkey door (exists on newsroom.sgit.ai and pki.sgit.ai). Exact, from door.js:

prf input   = SHA-256("<rp>/door/v1")
door seed   = HKDF-SHA256(ikm = prf bytes, salt = SHA-256("<rp>"), info = "sgit/door/v1", 32)
passphrase  = hex(HKDF-SHA256(ikm = seed, salt = empty, info = "sgit/door/v1/passphrase", 32))
vault id    = 8 chars of [a-z0-9] from HKDF-SHA256(seed, empty, "sgit/door/v1/id", 64),
              a byte used only when < 252
recovery    = the same, with the 16 bytes of a 26-character base32 recovery code as the ikm

<rp> is pki.sgit.ai on the register. The chain is passkey to door vault to master vault to book vault. The master holds the private keys in sgit's key store layout (`keys/sha256_<fp>/{metadata.json, private_key.pem, public_key.pem, signing_private.pem, signing_public.pem}), identity.json, doors.json, book.json, inbox.json` and .vault/access-token.json. Test vectors checked against sgit's Python are published at newsroom.sgit.ai/passkey/vectors.json.

Two findings from that work that shape this plan:

  • The passkey is a lock, not an identity. Key pairs are generated at random and stored in the master; they are never derived from PRF bytes.
  • One door per path. The same passkey gave different PRF bytes through the QR (hybrid) path than on the device. The design treats an unknown address as "no door here for this path yet" and offers the recovery code or adding a door from an open device.

4.2 Privacy posture, stated the way the family states it

  • Default and only mode in v1: device-local. The app makes no network request during record, transcribe or debrief, other than Apple's own model-asset downloads.
  • The vault server sees what sgit.ai says it sees: vault id, object sizes, timing, object counts. Never filenames, contents or keys.
  • No analytics, no telemetry, no third-party SDKs.
  • The honest sentence for the UI: "Transcribed and summarised on this device by Apple's models. Nothing was sent to us or to anyone else. Written by a model, not a stenographer: check anything that matters against the audio."
  • The App Store privacy label should come out as "Data Not Collected". Verify at submission.

5. The pipeline on Apple's models

5.1 Stages

The web app's workflow file is reused as a format: workflow/standard-ios.json, same schema, run by a Swift state machine in VDCore. Budgets become time ceilings, since nothing costs money.

Rules carried over unchanged: the transcript is never overwritten by a translation; nothing from classify is fed back into a prompt; a failed optional step degrades and says so, a failed transcribe aborts.

5.2 The four hard parts

Language has to be known before transcription. The web pipeline lets the model work out the language; SpeechTranscriber needs a locale up front. v1: the user's chosen language (default: device language, remembered per input source) with the choice visible before the run, and a one-tap "wrong language, run again". After transcription NLLanguageRecognizer checks the text and warns on a mismatch. An automatic guess (transcribe the first 15 seconds in each of the user's keyboard languages and pick the most confident) is a later improvement that spike S2 should cost.

The on-device model's context is small. The iOS 26 on-device model has a 4,096-token window for instructions, input and output together. A five-minute voice note can exceed it. So summary is map-reduce from day one: split the transcript on sentence boundaries into chunks with a token budget, extract key points and actions per chunk with guided generation, then merge into the three sections in a final pass. Every bullet keeps the time range of the chunk it came from, which gives the [hh:mm:ss] citations MeetScribe's debrief has. Spike S2 measures the real limits on the iOS 27 model before the chunk size is fixed.

Not every device or language has the models. Three independent availabilities, each checked at launch and before a run, never guessed:

CheckIf missing
SpeechTranscriber supports the locale, assets installedOffer the download; if the locale is unsupported, say so and offer DictationTranscriber as a lower-quality path
SystemLanguageModel.default.availability (device not eligible, Apple Intelligence off, model not ready)Transcript-only mode, stated plainly, with the reason and the Settings link. The app is still useful
The model supports the debrief languageSummarise in a supported language and translate with the Translation framework, labelled as translated

Apple Intelligence needs an iPhone 15 Pro or later, or an iPad with an M-series or A17 Pro chip. SpeechTranscriber reaches more devices. The App Store listing must say what works where. pt-PT against pt-BR matters to this product: which Portuguese each Apple model supports is a spike S2 question, not something to assume.

Guardrails will refuse some real voice notes. The system model refuses or truncates on content it classifies as unsafe, and a family voice note about a hospital visit can trip it. Treat a guardrail error as a degraded step ("Apple's model declined to summarise this. The transcript is complete."), never as a crash and never retried with altered text.

5.3 Prompts and evaluation

  • Prompts live as markdown in the app bundle under Prompts/, copied from website/app/prompts/ at a recorded commit and then adapted, because a 3-billion-parameter model needs shorter and more literal instructions than Gemini. The four locales and their tone lines (en-gb, en-us, pt-pt, pt-br) carry over.
  • Guided generation replaces "return JSON only" wherever the output is structured.
  • A fixed corpus of real voice notes (the user's own, with consent, never committed in plaintext; an encrypted vault is where they belong) is run through the pipeline on a device and scored: key points present, no invented actions, section format exact. iOS 27's Evaluations framework is the intended harness; a plain XCTest runner is the fallback.

6. Account: passkey, doors, vaults

6.1 The flow, identical in shape to pki.sgit.ai

 passkey ──PRF──▶ door vault ──holds the key of──▶ master vault ──holds the key of──▶ debriefs vault
 recovery code ─▶ recovery door ──────────────────────┘                └─▶ book vault (pki.sgit.ai's, untouched)
  1. One button. "Continue with a passkey" runs an assertion with the PRF extension and the fixed input SHA-256("pki.sgit.ai/door/v1"). If the user has no passkey for the site it runs a registration (with PRF requested) and then the assertion.
  2. Derive the door from the 32 PRF bytes (VaultDoor, with the site constant made a parameter: today it is fixed to web-summit.newsroom.sgit.ai).
  3. Look for the door at its derived address. Three outcomes: The user is signed in, with their identity and their debriefs, on a new device, having typed nothing. are kept on the device, encrypted with AES-256-GCM under HKDF(door seed, "voicedebrief.ai/local/v1"), the same idea as pki.sgit.ai's pki.local.v1 entry. Everything works except sync. write a recovery door; show the recovery code once.
    • Found: read master-key.json, open the master, read the debriefs vault key, open it.
    • Not found, no access key: the local account. The debrief store and the identity
    • Not found, access key present: create the master, the debriefs vault and the door;
  4. Add the access key later (paste, QR, or opening a sealed m1 link from pki.sgit.ai): the local account moves into vaults, and the key is stored at .vault/access-token.json in the master so no other device asks for it again.

The master gains one file, voicedebrief.json ({ v: 1, vault: "<prefixed vault key>" }). Nothing pki.sgit.ai wrote is changed, so an existing register account opens in the app and an account made in the app opens on pki.sgit.ai.

6.2 The passkey in a native app

  • API: ASAuthorizationPlatformPublicKeyCredentialProvider(relyingPartyIdentifier: "pki.sgit.ai"), with the prf field on the registration and assertion requests (iOS 18 and later). PasskeyPRF in PTVaultUI already does the assertion half for promptugal.news; registration with PRF is to be added.
  • Requirement on pki.sgit.ai: an apple-app-site-association file at https://pki.sgit.ai/.well-known/apple-app-site-association listing the app under webcredentials, and the webcredentials:pki.sgit.ai Associated Domains entitlement in the app. It is one static JSON file, but it is a change to another site and it makes that site vouch for this app, so it needs your sign-off and a note in that site's own record.
  • There is no server to issue or verify a challenge. The app generates a random one and discards the signature, as the web pages do. The passkey is used as a key-derivation device, not for authentication to anyone. Say so in the security notes.
  • User handle. iCloud Keychain replaces a passkey that has the same user id for the same site. The app must always try an assertion first and only register when there is none, and a registration must use a fresh random user id.
  • Same bytes as Safari? Expected yes: same credential, same input, platform path, iOS 18.4 or later. Apple's engineers have said the values should match. I could not find it confirmed for the native API against Safari, so it is spike S1. If they differ, nothing breaks: the design already calls that "another path, another door", added once from the recovery code or from an open device.
  • Third-party password managers (1Password, Google Password Manager on iOS) may not return PRF bytes through the native API. On no PRF output the app says which store answered and offers the ladder: use iCloud Keychain, or use the recovery code.
  • The door seed is cached in the Keychain (WhenUnlockedThisDeviceOnly, biometric access control) so opening the app is Face ID, not a passkey sheet every time. Signing out deletes it.

Three rules from sgit.ai's write-up that the Swift writer must keep, each with a test: never move the named ref unconditionally; refs are never cached while -imm- objects always are; and read the ref once after create, not before every publish, or compare-and-swap silently becomes overwrite.

Keeping in step with the format. The interop job (ios-vault.yml) comes across with the package and is extended to run in both directions and on a weekly schedule against the newest sgit-ai release, so a format change is noticed the week it lands rather than when a user's vault fails to open. The alternative, running the pinned JavaScript library in a hidden web view, stays on the shelf as the fallback if the format moves faster than the Swift writer can follow.

/index/<device id>.jsonl                   one line per debrief this device wrote
  • <id> is a time-sortable id made on the device. A debrief folder is written once, as one commit, so two devices never edit the same file and merges are fast-forwards or trivially clean. Edits (a corrected transcript line, a retitled debrief) are new files in an edits/ subfolder, MeetScribe's revision-layer rule.
  • Totals and the library list are recomputed from the records, never stored, as the newsroom's reader vault does.
  • Each device commits to its own clone branch (ios-<8 chars>), as sgit.ai requires.
  • manifest.json carries: id, created, device, source (recorded, imported, shared), duration, locale, the classify facts, the SHA-256 of every sibling file, the engine and model identifiers with OS version, per-step durations, and costUsd: null.
  • Because it is an ordinary vault, sgit clone <vault key> on a laptop and the vault browser at dev.vault.sgraph.ai both open it. That is acceptance test number one.

6.5 Sync

Local first. DebriefStore is the source of truth on the device; VaultSync is a queue.

  • A finished debrief is queued, written as one commit, then published with compare-and-swap. On ECAS: merge, publish again.
  • Pull on app foreground and on pull-to-refresh. Refs are never cached; -imm- objects are cached forever on disk, keyed by id.
  • Uploads continue in a background URLSession where the engine allows it; otherwise they resume on next foreground. Audio over 4 MB goes through the presigned upload path.
  • The UI shows, per debrief, one of: on this device only, queued, in the vault.

7. Identity: one bundle

"One identity" in v1 means exactly one sgit key bundle per account, with role master. No personas.

  • Create. RSA-OAEP 4096 and ECDSA P-256, generated on the device at account creation. RSA-4096 generation takes seconds on a phone: run it off the main actor with a visible step, and start it while the user reads the recovery code.
  • Or adopt. If the master already holds a key (the user made one on pki.sgit.ai), the app uses it and generates nothing.
  • Or import. Two private PEMs and a passphrase from an existing sgit pki key store, with the public bundle recomputed rather than trusted.
  • Where it lives. In the master vault, in sgit's key store layout, private halves as plain PKCS#8 inside the encrypted vault, exactly as pki.sgit.ai stores them. A copy sits in the Keychain behind Face ID for offline use. The Secure Enclave is deliberately not used: it cannot hold RSA keys or export anything, and this identity has to be the same on the iPhone and the iPad.
  • What the app does with it in v1. of the other files. sgit pki verify manifest.json manifest.json.sig checks it. public bundle".
    • Signs every debrief: a detached signature over manifest.json, which holds the hashes
    • Shows the identity: label, both fingerprints, a QR code of the k1 key link, and "copy
    • Opens a sealed message addressed to it, which is how an access key arrives (D5).
  • What exists and what does not. LaneCrypto already does the envelope, fingerprints and the SPKI conversions with imported keys. To add: RSA-4096 and P-256 generation (SecKeyCreateRandomKey, CryptoKit), PKCS#8 export and import, the bundle JSON, the key store files, detached signatures, and reading sgit's passphrase-encrypted private keys (PBES2 with PBKDF2-HMAC-SHA256 and AES-256-CBC, through CommonCrypto).
  • Milestone 6, after v1. Seal a debrief to a contact's bundle (envelope v2) and hand it over as a link or file. When that is built, sign the whole envelope, not only c: sgit.ai documents that today's signature covers the ciphertext alone.
  • Out of scope. Publishing to the register. That is a reviewed commit on pki.sgit.ai, and the app can export the submission JSON for it without doing more.

9.2 CI, carried over

Agents work in Linux containers and cannot compile Swift, so CI is the compiler and the pipeline from PrompTugal__App__iOS is the proven way to work like that. Bring across:

WorkflowWhat it does
ios.ymlLinux jobs plan and gate; one macOS job (macos-26) builds for the generic simulator unsigned, runs package tests on the host, then iPhone and iPad simulator tests one at a time; on a green dev push it archives, signs and uploads to TestFlight
ios-vault.ymlSwift writes vaults on macOS; sgit-ai on Linux clones and verifies them. Extend to both directions, to PKI (sgit pki import, encrypt, decrypt, sign, verify), and to a weekly schedule
screens.ymlOne XCUITest per screen, driven by launch arguments with sample data; PNG artefacts for iPhone and iPad. This is how an agent sees its own UI
testflight-ops.yml, ios-submit.ymlApp Store Connect operations and manual review submission
website.ymlVersion bump, tag, deploy the site

Lessons already paid for there, to keep: one Mac job per push (the macOS pool is five jobs and queue time was about three times run time); never boot a simulator while compiling; build for generic/platform=iOS Simulator; run-and-summarize.sh copies error: lines into the job summary so an agent can read a failure through the Actions API; archive unsigned and codesign afterwards, because automatic signing created a certificate per run and hit the account limit.

What CI cannot do, and who does it. No simulator has Apple Intelligence models, a microphone worth testing, or a passkey in iCloud Keychain. So:

  • Logic is tested in CI against protocols: a scripted Transcriber and LanguageModel replaying recorded real outputs (MeetScribe's "replayed real responses" rule), a folder vault transport, an in-memory secret store.
  • Speech, the model, the passkey and the share sheet are tested on a device by you, from TestFlight, against a written checklist per milestone. The app has a hidden diagnostics screen that runs the evaluation corpus and the spike measurements and exports the results as one JSON file, so a device run produces evidence an agent can read.

9.3 What only you can do

  • Create the App Store Connect record and the bundle id (the API cannot).
  • Add the secrets to the new repo's testflight environment: ASC_KEY_ID, ASC_ISSUER_ID, ASC_KEY_P8_BASE64, APPLE_TEAM_ID.
  • Enable the capabilities on the app id: Associated Domains, App Groups.
  • Publish the association file on the relying party's domain (D1).
  • Supply an SG/Send access token for the live write tests, as a CI secret, never in the repo.
  • Run the device checklists.

9.4 Conventions inherited from the VoiceDebrief repos

VERSION owned by CI; dev publishes; a reality document where anything not listed does not exist; briefs folder read-only for agents; issues-fs-lite under issues/; CHANGELOG with an Unreleased heading; llms.txt updated in the same commit as any public page; docs CC BY 4.0 and code Apache 2.0; British English and no em-dashes. M1. Repository and the key bundle (weeks 1 to 2, parallel with the spikes)

The repo skeleton from 9.1 with CI green on an empty app, SGitVault copied in with its tests and interop job passing unchanged, and PKIKit. Done when:

  • A dev push produces a TestFlight build.
  • VaultDoor, parameterised by site constant, reproduces every value in newsroom.sgit.ai/passkey/vectors.json, including the deterministic door record ciphertext and its object id.
  • The interop job passes in both directions: a bundle made in Swift imports with sgit pki import; a file sealed by sgit pki encrypt opens in Swift and the reverse; a Swift signature passes sgit pki verify and the reverse; an sgit passphrase-protected key store imports in Swift.
  • Fingerprints match pki.sgit.ai's keys.js for its five published fixture identities.

M2. Transcript on a device (weeks 2 to 3)

Record, import, share extension, decode, SpeechKit, the transcript view with audio seeking, DebriefStore local only. No account. Done when a WhatsApp voice note shared to the app becomes a time-aligned transcript with the phone in aeroplane mode.

M3. The debrief (weeks 3 to 4)

IntelligenceKit: classify, translate, map-reduce summary, the workflow runner and its progress view, the three availability checks and transcript-only mode, the evaluation corpus and runner. Done when the corpus passes the format checks and you have read ten debriefs and judged them usable.

M4. Account and vault (weeks 4 to 6)

AccountKit, the SGitVault additions from 6.3, VaultSync, the local account and the move into vaults, recovery code, identity creation and adoption, signing. Done when:

  • A debrief made on the iPhone appears on the iPad after a passkey gesture and nothing else.
  • sgit clone opens the debriefs vault and sgit pki verify passes on a manifest.
  • An account made on pki.sgit.ai opens in the app with its existing key, and the reverse.
  • Deleting the app and reinstalling restores everything from the passkey; with the passkey gone, the recovery code does.

M5. Hardening and release (weeks 6 to 8)

iPad layouts, App Intents, accessibility pass, localisation, security review (section 11), the site pages and llms.txt, App Store review notes that explain the passkey (reviewers need a path that does not require an access key: the local account is that path), TestFlight beta, then submission.

M6. After v1

Seal a debrief to a person; the Private Cloud Compute mode (D4); automatic language guess; import of MeetScribe's meetscribe/meeting JSON; opening a debrief on voicedebrief.ai from the vault with a read key.

For the AppSec review before M5 closes:

  • Keys in memory: the master's contents exist only while unlocked; zeroed on background after a timeout; never logged; no key-shaped string in any crash report or analytics (there are none).
  • The passkey ceremony verifies nothing (there is no server): confirm that nothing in the app treats a successful assertion as proof of anything except possession of the PRF bytes.
  • Vault content is untrusted input. A debrief written by another device is rendered as text and markdown, never as HTML with scripts.
  • The ciphertext rule from the website repo applies to this one: no vault key, access key or private key in the repository, with a pre-commit and CI scanner from the first commit rather than later (the website's issue 013 is still open on this).
  • Test fixtures use published fixture keys only (pki.sgit.ai publishes five).
  • File protection completeUnlessOpen on the local store; the App Group container holds a shared file only until the app picks it up.
  • Third-party code: none, by the iOS repo's rule. libopus is the one possible exception (spike S4), and it would need a written reason.
  • RSA through the Security framework means hand-written DER for SPKI and PKCS#8. That code is small and exactly where parsing bugs live: fuzz it, and test it against sgit's files.
