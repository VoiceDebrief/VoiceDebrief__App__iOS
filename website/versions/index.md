# Release history

Every release of this repository. Every push to `dev` is a release: CI works out the next number from the latest tag, writes the `version` file, tags, and publishes the site. Nobody sets a version by hand (since 13 November 2026; before that the number was set in the push). A row headed `next` has not been given its number yet.

| Version | Date | What changed |
|---|---|---|
| next | 13 November 2026 | The Lab, and its first experiment. Under Settings, a Lab section with L01, one prompt with tools on and off: type or pick a prompt, switch each tool on or off, and send one request to Apple's on-device model in a new session. The screen then shows everything: the instructions and prompt sent, the tools offered and kept back, each tool call with its arguments, result and time, the answer, the total time, and any error in plain words. Four tools that only read: the date and time, a list of notes, one note's transcript, and a choice of next screen that is recorded and not acted on. Six preset prompts say which tools a reliable model would call, and the screen counts how often it did. Runs are kept while the app is open and exported as JSON. Every request goes through one component, the model door, with a policy and a record; the debrief does not use it yet. In test: it compiles and its logic is unit tested, but CI has no model, so no request has been made. |
| next | 13 November 2026 | After the owner's notes on build 0.1.9: the Send buttons are a bar fixed at the bottom of a note, where the growing transcript and debrief cannot move them, and a note sent before it is finished goes the moment it is. The version is shown on the record screen and links here. |
| next | 13 November 2026 | Finishing a note saves it to a vault, at the owner's request (issue 022): once the note is done and its audio compressed, it is written into the vault chosen in Settings as one signed commit. On by default, with a switch; nothing happens until a vault exists. The note says where it was saved, or why it was not. |
| next | 13 November 2026 | Vaults are local first, and a server is a remote. Creating a vault no longer asks for an access token: a vault is made, saved into, read and browsed on the device, with no server and no network. Servers are added by name, with an address and an access token in the Keychain; a vault has none or one. Push and pull are separate, explicit steps that only ever move a branch forward: when the device and the server have both changed, the app says a merge is needed (not built) and overwrites nothing. Each vault says where it is: on this device only, not yet pushed, on the server too, ahead of it, or push failed and why. Vaults made by earlier builds (from v0.1.5) stay on their server and work as before, and can be copied to the device. Forgetting a vault now asks first and says what would be lost. In test: none of this has run on a device, and nothing has been pushed to a real server from the app. CI has `sgit` clone a vault that was created in one folder and pushed to another. |
| next | 13 November 2026 | The version is now CI's, as in the other VoiceDebrief repositories: every push to `dev` is tagged with the next number, the version file and the README badge are written by CI, and the site is stamped when it is deployed. The app's TestFlight version is that tag. |
| next | 13 November 2026 | A second app begins in this repository, for now: the sgit app (`Apps/SGit`, bundle `ai.sgit.vaults.app`), sgit as a native app, starting with photos, videos and large files into a vault. Its design and its own reality file are under [sgit-app](../sgit-app/design/index.md). The vault engine reads and writes files over 4 MB as sgit does (issue 023), encrypting from disk to disk, checked against sgit in both directions by a new workflow, `sgit-app.yml`. Nothing of the sgit app has run on a device. The version is now CI's, as in the other VoiceDebrief repositories: every push to `dev` is tagged with the next number, the version file and the README badge are written by CI, and the site is stamped when it is deployed. The app's TestFlight version is that tag. |
| v0.1.9 | 13 November 2026 | Recipients. A note can be sent to anybody who has given you their lane: a person, another device, an agent session. Add one under Settings or from a note by scanning their QR code with the camera, choosing a picture of it, or pasting the link; the code may carry their name. A note has one Send button per recipient. A recipient's own QR code can be shown, to pass them on. The developer's lane built into the test build is the first recipient and still asks before sending; one you added yourself sends at once. For the other side, `tools/conductor/conductor.py` makes an inbox (a key pair, a vault, a lane), prints its link or QR code, and opens what arrives. The app now asks for the camera, only to read a QR code. In test: nothing here has run on a device. A later build of this version changes the record control, at the owner's request: it is green, and while recording shows a tick and finishes the note; Discard is a small red word at the top that asks before deleting. |
| v0.1.8 | 13 November 2026 | An experiment, at the owner's suggestion: a clean text. A note can be rewritten as full sentences by Apple's model, a passage of about 110 words at a time, with nothing meant to be left out. The model is given the speaker's own words (Settings, Your words), because Apple's speech model cannot be: `SpeechTranscriber` ignores contextual strings. It returns structure, not prose (guided generation), including up to three phrases per passage it could not follow, each with a question; an answer is kept and joins the speaker's words. The screen can show what was changed, word by word, and warns when a rewrite is under half the length of what was said. The clean text travels with a note sent over the lane. Also: the record screen follows the live words. In test: no clean text has been made on a device. |
| v0.1.7 | 13 November 2026 | Build A of the [design](../design/index.md): capture without loss, and a new shell. A note is created when recording starts and the recording is written straight into it as WAV, a form that can be repaired if the app dies before the file is closed; it is compressed only after the note is finished. A call or another app taking the microphone ends the recording and keeps it. Every note is kept on the device: a Library tab lists them by day and a note can be reopened, run again or deleted. Stopping opens the note at once and it fills in. Four tabs (Record, Library, Vaults, Settings) that become a sidebar on wide screens; a record screen with one large control; developer tools moved under Settings. The background audio mode is declared; recording with the screen locked is untested. A later build of the same version makes the record screen follow the live words, after the owner found they ran off the bottom. |
| v0.1.6 | 13 November 2026 | The debrief prompt again, after the first note sent over the developer lane: the model wrote "Speaker is..." and "[Speaker]" because the prompt itself said "the speaker". It now says the note is the reader's own, asks for plain statements with no subject, and marks the reader's tasks [me]. |
| v0.1.5 | 13 November 2026 | Vaults. The vault engine can now create a vault, in the form `sgit init` writes; CI has `sgit` clone a vault Swift created. A Vaults tab: keep an SG/Send access token in the Keychain, create a vault, add one made elsewhere by its key, and look inside (head, files, history, branches, the key, and every request, decryption and signature check the engine made). After a run, save the debrief, transcript, run and audio into a vault as one signed commit. In test: no vault has been created from a device yet. |
| v0.1.4 | 13 November 2026 | The developer's lane is built into the test build, at the owner's request, so a note can be sent without pasting a link first; a pasted link still takes its place. Sending still happens only when the button is pressed. |
| v0.1.3 | 13 November 2026 | While recording: the words appear as they are spoken, and moving bars show the microphone is being heard. The live text is a preview; the transcript that is kept is still made from the recorded file when the recording stops. And a way to help judge the models: with a lane link pasted on the Diagnostics tab, a button after each run sends that note (audio, transcript and debrief) to the developer over an sgit append lane, encrypted on the device to the developer's key. Nothing is sent without pressing it. |
| v0.1.2 | 13 November 2026 | The debrief prompt, changed after the first real runs on an iPhone and a Mac: the model was copying quotation marks from the prompt's examples, renaming a heading, repeating a one-line note back as its own key point, and turning a passing remark into an action. The prompt now shows the shape with no quotation marks, says the speaker's own tasks are theirs, and says what is not an action. A note of fewer than 25 words is no longer sent to the model: the transcript is the whole note. |
| v0.1.1 | 13 November 2026 | The first feature, as the plan's quality spike: record a voice note or choose an audio file, transcribe it on the device with Apple's `SpeechAnalyzer`, and write a debrief with Apple's on-device model, reading a long note in parts. A diagnostics screen reports what the device says about both models and exports it. Nothing is saved yet. In test: nobody has judged the results on a device. Also: the TestFlight upload, proven by build 0.1.0 (4), installed on an iPhone and a Mac. |
| v0.1.0 | 13 November 2026 | The repository starts. An iPhone and iPad app that builds and tests, with one screen that says what is and is not built. The `SGitVault` vault engine copied from `PrompTugal__App__iOS`, with the door derivation made to work for any site and checked against the published vector. CI: build and test on a Mac, vault interop with `sgit`, and this site. The plan, published. |
